# 公告中心首次访问单弹窗多公告浏览设计

## 背景

当前首页公告中心在首次进入时，只会自动展示第一条未读公告。若接口返回多条未读公告，其余公告仅保留在公告列表中，首次访问阶段缺少连续可见的提醒能力。

当前公告中心组件位于 `web/src/components/AnnouncementCenter.tsx`，并在 `web/src/App.tsx` 中同时用于移动头部与桌面信息栏。现有已读记录使用本地存储键 `gpt2api.announcement.read.ids`。

本次调整目标是：首次进入首页时，若存在多条未读公告，只弹出一次窗口，并在同一个弹窗内顺序浏览全部未读公告。

## 目标

实现以下行为：

1. 首次进入首页且存在多条未读公告时，仅展示一个弹窗。
2. 弹窗内支持在未读公告之间切换，并明确显示当前位置。
3. 当前公告确认后写入本地已读集合，并顺序推进到下一条未读公告。
4. 右上角关闭仅关闭窗口，不写入已读。
5. 公告入口与公告列表能力继续保留。
6. 避免 `AnnouncementCenter` 双挂载导致的重复请求与重复弹窗。

## 非目标

本次调整范围内不包含以下内容：

1. 公告后端接口结构变更。
2. 公告列表页样式的大范围重做。
3. 已读状态同步到服务端。
4. 公告富文本能力扩展。

## 交互方案

### 首次自动提醒

当首页进入激活状态后，公告中心读取公告接口数据，并结合本地存储中的已读 ID 计算未读公告集合。

当未读公告数量大于 `0` 时：

1. 仅打开一个公告弹窗。
2. 默认展示未读集合中的第一条。
3. 在弹窗中显示当前位置，例如 `第 1 条，共 3 条`。

当未读公告数量等于 `0` 时，不触发自动提醒，仅保留右上角“公告”按钮。

### 弹窗内浏览

弹窗保持当前视觉结构：图标、标题、正文、操作区。

在操作区中补充以下能力：

1. “上一条”：浏览上一条未读公告。
2. “下一条”：浏览下一条未读公告。
3. “知道了”：确认当前公告。
4. “公告列表”：打开完整公告列表。

交互细节如下：

1. 位于第一条时，“上一条”置灰或隐藏。
2. 位于最后一条时，主确认按钮显示“知道了”。
3. 中间条目阶段，右侧主按钮可显示“知道了并继续”或继续使用“知道了”，点击后写入当前公告已读并切换到下一条。
4. 浏览切换本身只改变当前索引，不写入已读。

### 已读写入时机

已读写入只发生在点击“知道了”时。

点击“知道了”后的行为：

1. 将当前公告 ID 写入 `gpt2api.announcement.read.ids`。
2. 若后续仍存在未确认的未读公告，则弹窗保持打开并切换到下一条。
3. 若当前已是最后一条未读公告，则写入后关闭弹窗。

### 关闭行为

点击弹窗右上角关闭按钮时：

1. 仅关闭当前弹窗。
2. 当前未确认公告保持未读。
3. 下次再次进入首页时，仍可再次触发自动提醒。

### 公告列表

“公告列表”保留现有作用：展示全部公告，而非仅展示未读公告。

首次自动提醒弹窗与公告列表弹窗属于两个层次：

1. 自动提醒弹窗：用于首次访问时顺序查看未读公告。
2. 公告列表弹窗：用于查看全部公告历史内容。

## 状态设计

建议在公告中心中维护以下状态：

1. `items`：接口返回的全部公告。
2. `unreadItems`：当前会话计算出的未读公告集合。
3. `popupIndex`：当前展示的未读公告索引。
4. `popupOpen`：首次提醒弹窗是否打开。
5. `listOpen`：公告列表弹窗是否打开。
6. `loaded` 与 `loading`：沿用现有加载控制。

辅助方法保持现有模式：

1. `readIDs()`：从本地存储读取已读公告 ID。
2. `writeIDs(ids)`：去重后写回本地存储。

组件展示当前弹窗内容时，使用 `unreadItems[popupIndex]` 作为当前公告来源，替代当前单一的 `current` 状态。

## 组件结构调整

### 方案选择

当前 `AnnouncementCenter` 在 `App.tsx` 中挂载两次，存在重复请求与重复弹窗的可能。

本次设计采用“单实例挂载”的处理方式：

1. 在 `App.tsx` 中只保留一处 `AnnouncementCenter` 实例。
2. 需要同时在桌面与移动区域显示入口时，将“公告按钮外观”与“公告状态管理”拆分。
3. 入口按钮可作为轻量子组件复用，实际数据请求与弹窗状态只保留在单个上层实例中。

这样可以保证：

1. 公告接口只读取一次。
2. 自动提醒只触发一次。
3. 已读写入来源唯一。

若当前页面结构调整成本偏高，可在组件内部增加单实例保护作为补充，但首选仍是单实例挂载。

## 异常处理

### 接口失败

公告接口请求失败时：

1. 页面其他区域继续正常显示。
2. 公告按钮继续保留。
3. 自动提醒弹窗不展示。
4. 手动点击公告按钮时，允许再次尝试读取接口。

### 本地存储异常

本地存储中的已读数据解析失败时：

1. 按空数组处理。
2. 在下一次正常写入时覆盖为合法 JSON。

### 边界情况

需要覆盖以下边界：

1. 接口返回空数组。
2. 接口返回的全部公告均已读。
3. 接口返回部分公告已读、部分未读。
4. 用户浏览中关闭弹窗后，下次进入再次从第一条未确认公告开始展示。

## 视觉与可达性

1. 继续使用现有 `dialog` 结构与 `createPortal` 挂载方式。
2. 标题保持 `aria-labelledby` 关联。
3. 当前公告切换时，标题与正文同步更新。
4. 在正文下方或按钮区上方显示位置提示，例如 `第 2 条，共 5 条`。
5. 移动端按钮区允许换行为两层结构，保证操作区域尺寸稳定。

## 测试方案

测试文件为 `web/src/components/announcement-center.test.tsx`。

至少覆盖以下行为：

1. 存在三条未读公告时，仅展示一个弹窗实例，并显示 `第 1 条，共 3 条`。
2. 点击“下一条”后，展示第二条公告，弹窗持续打开。
3. 点击“知道了”后，将当前公告写入本地已读集合，并切换到下一条未读公告。
4. 最后一条点击“知道了”后，弹窗关闭，本地已读集合包含全部已确认公告。
5. 点击右上角关闭按钮时，仅关闭弹窗，未确认公告不写入已读。
6. 已读公告仍可在“公告列表”中查看。
7. 接口失败时组件仍可渲染，且手动点击公告入口时可再次触发读取。
8. 在页面同时存在桌面区与移动区入口的布局中，公告接口只读取一次，自动提醒只出现一次。

## 验收标准

满足以下条件即可视为本次调整完成：

1. 首次进入首页且存在多条未读公告时，仅弹出一个公告窗口。
2. 窗口内可切换多条未读公告，并清楚看到当前位置。
3. 点击“知道了”后，当前公告进入已读并顺序推进。
4. 关闭窗口后，未确认公告仍会在后续重新进入首页时出现。
5. 桌面与移动布局下均不会出现重复弹窗或重复请求。
6. 现有公告列表入口仍可使用。
7. 相关自动化测试全部通过。
